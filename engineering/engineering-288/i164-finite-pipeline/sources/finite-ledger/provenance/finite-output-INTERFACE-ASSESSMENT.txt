INDEPENDENT INTERFACE ASSESSMENT — 24 OCTOBER 2026

The public authenticity boundary is verify_finite.run(component, consumer,
submitted), and the CLI that invokes it. check(value, bundle) is an internal
operation requiring trusted inputs. It is not an authenticity service for
caller-supplied bundles. No change to that boundary is adopted in this review.

run authenticates the exact 60-member finite-input component and 40-member
consumer archive on every call: regular-file check, whole-archive identity,
CRC, safe exact manifest membership and all member sizes/hashes. trusted then
checks the saved bundle hash and the three consumer source identities against
the candidate-member manifest. It parses fresh expectations from the exact
bundle. It does not accept a detached prior success receipt as current output.

The submitted file is read as actual bytes. Duplicate JSON keys and nonfinite
constants reject. The structural check compares every required output field
against either fixed source-defined status fields or the authenticated bundle.
The submitted byte hash is calculated for receipt attribution after successful
correspondence checks; no expected saved-output hash alone decides acceptance.
Truthfully attributed reserialization of the same JSON representation is
allowed. Receipt identities identify the exact submitted bytes, not complete
current model bytes or a canonical registered model identity.

Every context is separately checked, with explicit declared order. Each token
has an exact local integer index, acquisition/context/local occurrence key,
class, canonical lowercase payload encoding and complete pinned metadata.
Equal payloads do not merge keys. Positions are retained projected record
indices, JSON pointers and framing provenance; they are not physical offsets
in an original database or wire packet. Laboratory model/configuration digest
values remain observed payload, not verified current model identities.

All 9,339 groups/context, including empty groups, retain the exact directory,
production expressions, visibility and custody fields. Half-open ranges form
one contiguous partition of the 2,376 local tokens. Member lists and row tuples
must exactly correspond to those tokens. The two contexts remain symbolic
domains; their presence establishes no doubled physical storage allowance.

The recovered historical Group/Seq interface and prospective Group contract
support bounded entries(None), unique get(key) and parts usage here. The
historical pairs PARENT-RECORD branch resolves each source row's parent key
against the target role, preserving source order. With old_rel_n=0 and new=True
in this prospective contract, each matched finite source row yields an edge.
The verifier implements this as a dictionary join rather than invoking pairs.
The reviewer separately checked it using a sorted merge of role keys followed
by restoration of source-row order, comparing every ordered endpoint and key
to the pinned pair rows and the actual saved representation. Historical prepare,
global offsets, even-count/equal-half assumptions and Cartesian joins are not
part of this contract. No historical native procedure was executed here.

There are 9,376 ordered lookup steps/context and 2,368 realized edges/context:
2,365 structural plus three semantic. The exact inherited ordinals, source and
target role keys, context/acquisition qualification, per-rule rows and ordering
are preserved. Twelve n-ary fold duties/context are separately retained and
never converted into extra Cartesian pairs. Mechanical lookup does not qualify
semantic dependency, exposure, custody, authority or operational coverage.

Exact duties include mechanical rows, fold obligations and retained procedure
results. All three O01–O11 sets (SOURCE-ONLY, model and ledger) and their retained
status mappings are compared in full. UNKNOWN, UNAVAILABLE, unresolved
cardinalities and explicit blocked states remain authoritative. Snapshot-empty
groups do not make production quantities zero; finite counts do not establish
lifetime caps or complete production coverage.

Returned receipt structures contain freshly allocated dictionaries/lists and
scalar values, not references to mutable expectation objects. Expectations are
read afresh on repeated public calls. Mutating returned context order, nested
counts, byte identities and statuses cannot change subsequent validation.

The new executable is standard-library-only and does not import consumer.py,
finite_inputs.py, pairs, prepare, bind_ledger or a full-model verifier. Exact
recovered source copies are provenance, not dynamically imported implementation.
The archive pins provide their authentication; changing local provenance copies
cannot authorize a different input archive. As with the retained contract,
implementation/code integrity and a trusted process are prerequisites. This is
not a hostile concurrent filesystem/process integrity or resource-exhaustion
security claim. Certain malformed shapes may raise ordinary Python exceptions;
CLI failures are preserved and do not produce a successful verification receipt.

This verifies one saved finite representation from one already reviewed saved
acquisition. It is not new producer execution, general acquisition admission,
complete native-model verification, ledger construction/rebinding, native model
serialization, canonical registration or operational readiness. The exact
predecessor input/projection/procedure reviews are reused, not rerun or relabelled
as current producer coverage.

A broader construction still requires a source-established complete-native
serialization/descriptor and verification-input contract, including directory
and relation integration. Production instantiation additionally requires the
protected production occurrence domains, lifetime multiplicities and appropriate
authority/operational evidence. No policy, new cap, retention amendment or outcome
restriction is adopted by this finite verification step.
