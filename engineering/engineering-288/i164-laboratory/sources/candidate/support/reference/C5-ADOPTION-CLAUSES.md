# Decision proposal — staging remains unadopted

Recommendation: approve the following **design scope for subsequent implementation**, without authorizing an occurrence, deployment, qualification, or operational admission. Aurora delivery feasibility remains unknown. Staging is a candidate means to divide work; these results do not prove it necessary or feasible on the deployed network.

1. Version the original-message authorization carrier as the V2 proposal in TRANSITIONS.md. Preserve all historical V1 signatures and the separate accepted four-file V2 evidence authentication. No digest-signing or Ed25519ph substitution. Approve the explicit carrier/typed-value bounds only for this candidate; verify their adequacy against the owning profile before implementation completeness is asserted.
2. Permit **one lifetime staged session**, as a subset of the existing at-most-64 submission envelope, with 512-byte append payloads (last payload 41 bytes at maximum M). No failed/abandoned session replacement under this one-session reservation. A new U or configuration does not replenish any allowance.
3. Reserve at most **2,070 submitted transaction attempts**, including 16 shared retries/failed attempts, and one charged reconciliation observation for each attempt plus 16 extra charged polling/recovery requests: **2,086 staging queries**. Internal repair emits no observation. When an allowance is exhausted, stop before external observation/submission; retain retirement and freeze uncertainty. No automatic retries.
4. Change the **shared lifetime query limit from 1,024 to 3,110**, preserving the original 1,024 capacity for the other governed operations, not creating a fresh counter. Preserve Pilot001's already consumed one query. Staging reservation is a partition inside this shared total. Both aggregate and partition checks must occur durably before the governed action, including concurrent requests and failed/interrupted attempts.
5. Keep the **shared 130-snapshot allowance**. Reserve 85 staging backup attempts: begin, every 32 accepted appends including the final partial batch, finalization, terminal result, cleanup, plus 16 additional failed/repeated backup attempts. With the recorded one consumed backup, 44 remain for other operations. Ordinary chain state commits are not silently reclassified as off-chain backups. A different snapshot definition would require recalculation.
6. Conservatively charge both cryptographic signature finalization invocations and proof-verifier invocations against the existing shared **64-verifier-invocation allowance**. Reserve 18 for this session (one of each plus up to 16 failure/retry invocations). This is a proposed explicit classification, not a claim that the prior directory already includes signature-finalizer occurrences. Actual release still requires all qualification prerequisites. Internal hash compression blocks are not separate verifier calls.
7. Keep the existing four roles, two contexts, 32 cases, two concurrent submissions, 384 comparisons, eight setup transactions, 24-hour lifetime, adversary bounds and per-game/target/coalition 2^-128 risk ceiling. No assertion that time remains on Pilot001 or that deployment fits the setup allowance. No lifetime reset. The lifetime origin/remaining time and setup plan must validate before any execution proposal.
8. Adopt the explicit state transitions, abandonment/recovery and immutable input/receipt bindings in TRANSITIONS.md as implementation requirements. Finalized authentication authenticates inputs only. Both signing methods must execute their retained guards and live EQ/MC at the indivisible comparison/effect cut. No synthetic qualification or cached comparison verdict may release an effect.
9. Before execution, register every stage, attempt/result, hash/parser state, receipt, query, backup, seal, release and cleanup occurrence; update ownership/dependency/visibility, directories and ledger. Rebind candidate identities and mark changed stream identities uncomputed. Adoption does not assert that those updates or the incremental EVM implementation exist.

Alternative: retain all current limits and decline this serial-reconciliation design. Neither the 512-byte nor 1,024-byte maximum-message schedule fits the remaining query allowance. Batched reconciliation or a smaller message envelope would be separate designs requiring exact occurrence/failure coverage; neither is silently selected here. The full 64-session maximum does not fit the snapshot/verifier limits and is not recommended for this checkpoint.
