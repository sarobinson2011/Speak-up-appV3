# Privacy Engine Complete Implementation Profile V1

Composition date: 2026-08-12.

STATE.md remains the single canonical development authority.

Protocol authority always remains with the published Privacy Engine protocol generation.

## 1. Profile Status

This document is the composed Privacy Engine Complete Implementation Profile V1.

Profile status: **composed**.

It is derivative of Privacy Engine Protocol Specification V1 and normative only
as the identified implementation-facing profile target. It is not a new protocol
generation, Protocol Specification amendment, Protocol Publication, or source of
protocol semantics.

## 2. Purpose

This profile provides one uniquely identified, bounded, complete, and
implementation-facing target for realizing the complete protocol-owned Privacy
Engine capability chain without application coupling or implementation-specific
prescription.

## 3. Scope

The profile processes every one of the 729 published normative requirements and
records exactly one specification-derived disposition for each requirement.

It defines applicability for the Generic Complete Privacy Engine Protocol
Implementation Target. It does not define an implementation, assess the current
codebase, or perform compatibility, conformance, certification, security, or
operational-readiness assessment.

## 4. Authority and Dependency Position

The governing direction is:

> Published Protocol Generation
> -> Published Protocol Specification
> -> Implementation Profile
> -> Implementation
> -> Conformance
> -> Certification

The profile derives from the specification. Implementations realize the profile.
No downstream layer acquires authority over an upstream layer.

## 7. Selected Implementation Target

The selected target is the Generic Complete Privacy Engine Protocol
Implementation Target: one complete composite implementation class capable of
realizing the protocol-owned semantics applicable to an end-to-end Privacy
Engine operation.

The target is generic, application-independent, implementation-neutral,
portable, independently implementable, independently assessable, and complete
relative to the protocol-owned capability chain.

It is not petition-, repository-, deployment-, technology-, topology-, or
current-implementation-structure-specific.

## 8. Included Protocol Capabilities

The target includes:

- anonymous membership, private-secret continuity, and enrollment separation;
- proof generation, declared public inputs, verification, evidence, and complete validity;
- nullifier uniqueness and action-bounded unlinkability;
- Protocol Operations, Protocol Actions, applicable rules, Evaluation, and Determination;
- acceptance, rejection, and accepted no-transition behavior;
- transition mappings, preconditions, eligibility, authorization, execution, commitment, and atomicity;
- protocol state, successor state, evolution, history, public consequences, failure, staleness, and re-evaluation;
- Interface Contracts, Concrete Interface Specifications, Protocol Surfaces, and Published Results;
- runtime enforcement, execution, and reporting responsibility;
- the protocol-facing side of application integration;
- implementation and realization obligations;
- privacy, minimum disclosure, actor separation, semantic preservation, and applicable global exclusions.

## 9. Excluded Application and Implementation Material

The target excludes petition meaning and lifecycle, application policy,
metadata, UI, moderation, permissions, persistence, read models, outcome
interpretation, and application truth.

The application-owned adapter implementation is outside the target. The
protocol-facing interface and applicable semantic-preservation obligations at
that boundary remain included.

Programming language, source-tree structure, internal decomposition,
algorithms not constrained by the specification, database design, transaction
formats, relay architecture, transport, deployment topology, treasury
management, monitoring, provisioning, provider selection, and current
repository organization remain implementation or operational choices rather
than profile semantics.

## 10. Profile Composition Method

For each published requirement `R`, composition evaluates its complete row,
published applicability, authoritative SF home, definitions, cross-references,
dependencies, and relationship to the selected target.

> contains(S, R) -> exactlyOneDisposition(F, R)

No family-level assumption replaces the row-level record. Family ownership
provides context; the exact published applicability remains controlling.

## 11. Disposition Vocabulary

The permitted dispositions are:

1. `applicable`;
2. `conditionally applicable`;
3. `non-applicable` under an identified specification rule;
4. `resolved through permitted specification choice`.

Every ledger row uses exactly one disposition.

## 12. Applicability Rules

A requirement is applicable when it governs this profile, the selected target,
an unconditionally included capability, a necessarily produced downstream
surface, or an applicable privacy, authority, preservation, or exclusion
boundary.

All applicable requirements preserve their published identity, home, strength,
applicability, meaning, prohibitions, permissions, success behavior, failure
behavior, and traceability unchanged.

## 13. Conditional Applicability Rules

The row-level assessment found no target-level conditional disposition.

This zero count does not erase runtime or lifecycle applicability conditions.
Because the selected target is complete, it includes every protocol-owned
operational branch. Each applicable requirement retains its exact published
condition within its published applicability rather than being narrowed by an
additional profile-level condition.

## 14. Non-Applicability Rules

Non-applicability is recorded only where the requirement's published subject is
outside the selected target, the target expressly excludes that subject, and no
included capability or dependency activates it.

Non-applicability does not weaken, delete, invalidate, or reinterpret the source
requirement.

## 15. Permitted-Choice Rules

Exactly seven requirements receive a permitted-choice disposition. Each uses
published `MAY` authority. The profile retains or constrains only the published
choice space and introduces no implicit default.

The choices preserve implementation freedom for technical variation, concrete
interface realization, runtime responsibility allocation, internal technical
composition, implementation-facing choices, implementation multiplicity, and
realization multiplicity.

## 16. Dependency Rules

The selected complete target has no dependency on another Implementation
Profile.

All included capability dependencies are internal to this one complete profile.
Source-section, normative-requirement, runtime-component, source-code, and
deployment dependencies do not become separate profile dependencies.
