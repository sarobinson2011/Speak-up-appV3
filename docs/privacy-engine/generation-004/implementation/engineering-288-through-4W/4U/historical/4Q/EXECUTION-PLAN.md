# Full-stream execution plan — prepared, not launched

## Gates and distinct obligations

This is an execution preflight, not permission or a claim that missing inputs exist. Actual admission stays disabled. Two independently useful routes must remain separate:

1. **Conditional mechanical identity milestone:** enumerate/hash the retained binary stream, independently replay it, and separately compute/replay the static textual serialization identity. Its descriptors already exist. This can run without genuine qualification if explicitly labeled mechanical/conditional. Hash-only generation does not acquire a signed evidence bundle or produce a full-model witness.
2. **Full-model integration witness:** acquire exact source-owned records/guards/values, full required scopes, appointments, policy/ledger/assessor bytes and final profile bindings, then validate the actual supplied four-file bundles. Conditional implementation success and genuine qualified evidence are distinct. Prerequisites in inventory/REQUIREMENTS.jsonl must be resolved for the chosen claim before launch.

No compact substitute establishes exact byte-stream hashes. The 50 fixed tokens in 18 groups yield 1,169 excluded candidates; complement arithmetic exactly covers the retained predicate and count, including arbitrary/constant and cross-record combinations. This is sufficient for exact set-description/cardinality, not semantic qualification. Complete supplied rows still need legal membership, strict ordering/uniqueness and **separate** structural and potential counts. Under those conditions a supplied subset with exact required cardinality equals the required set. Counts alone are insufficient.

Whole-model semantic coverage additionally needs every source-owned target/view, qualified duty classification, complete actual occurrences/dependencies, exact/computational evidence, composition, budget and non-vacuity. Connectivity, a predicate descriptor, signature validity or the number of rows does not prove those duties.

## Acyclic final-model and profile dependency handling

Do not replace the retained 08d6… model or insert a guessed digest into it. Full stream computation produces a separate candidate record. Before witness signing:

1. Independently verified binary bytes produce the exact binary stream digest and row/byte counts.
2. Canonicalize a **new candidate model** with that equality-stream identity; record its bytes/SHA and a diff against the preserved provisional model. Even if tokens/templates/structural arrays are identical, the whole-model digest changes.
3. Re-evaluate every selected-contract/source/procedure reference for actual dependency on changed model bytes. Source definitions and the 4I amendment stay fixed. Reuse an unchanged contract only after exact dependency verification; do not automatically carry provisional model-bound ledger/scope/occurrence receipts forward.
4. Rebind ledger provenance, source/model joins, scope descriptors, owning-value/guard directories, applicability and assessor inputs that bind the model; independently govern immutable policy/templates and construct the final outer. Template-array digests may be unchanged only if exact canonical arrays remain identical.
5. Final outer digest enters outside occurrence records, arguments/assessments/invocation inputs and evidence.tsv. Compute exact tokens.tsv and links.tsv hashes, populate evidence.tsv with independently determined outcomes, then sign the exact original three-file message. Compute the four-file object digest only after signature.txt exists.
6. Reconstruct any dependent assessment invocation from its actual exact dependencies; re-acquire assertions/signatures for changed preimages. Rebuild scheduler input/prerequisite catalogs. Fresh jobs only; no historical receipt adoption under new profile/model/code identities.

This is a planned dependency transaction. No model, contract, profile or source byte was changed in 4Q, and no final digest was precomputed. A self-referential source-specific invocation or bundle must be rejected through its existing exact binding rules, not resolved by accepting a caller digest.

## Pass accounting and scope reuse

For one unique supplied static links file, budget the following work separately:

| Stage | Dominant reads/writes |
|---|---|
| Optional deterministic hash computation | One generation pass and one replay pass, neither materializes output with the retained worker |
| Actual file provision | One source write/delivery of N bytes; source signing/delivery costs are external and unmeasured |
| Fresh scheduler/catalog identity | At least one full N-byte exact input hash; all other input/artifact identities also checked |
| Four-file acquisition/object hash | One complete link read within exact length-prefixed object/constituent checking; outer/model/contract reads additional |
| Pure Ed25519 verification | One complete exact original-message read, N plus evidence/token/domain bytes; no safe SHA-512 verifier state export |
| Supplied-link validation | One N-byte parse/membership/order/ordinal/hash pass with retained full index |
| Terminal recovery reuse | Another exact input/artifact hash pass when resumed; completion receipt alone does not skip bytes |
| Semantic/ledger | Separate owning-record/projection/dependency/index reads; complete containing-object checks may repeat per field; not proportional to pair count |

This is a minimum dominant accounting scenario, **not an exact total pass count**. Scheduler prerequisite checks, source acquisition, repeated scope paths, partial stages and artifact reopen checks add exact reads. Both object and per-file prefix reconstruction can revisit the same prefix. Full semantic-byte volume and cache access pattern are unknown until inputs exist. The inventory records this uncertainty rather than claiming one-pass integration.

There are three scopes per required phase. Scope closure must be established from source-owned seeds; do not infer all scopes equal, connected, disjoint or identical. Identical token/link bytes can potentially share physical content after exact identity and correspondence are established; evidence rows, scope/profile joins and signatures are still independently validated. The current path-bound scheduler does not automatically turn three identical path aliases into one authenticated result. Plan separate scope processing by default. Actual occurrence equality may be much smaller than the static potential graph, but no size reduction is assumed without exact acquired values. Static plus E/PRE-EXECUTION/PRE-COMMITMENT is up to twelve phase/scope jobs in the planning matrix; their real byte totals are missing inputs, not twelve asserted full-size streams.

At 100–500 MB/s sustained storage/hash throughput, a single 19.91 TB read takes about **55.3–11.1 hours**. Four extra complete reads alone add 44–221 hours. A conservative **14–30 day sequential allocation for one unique static stream**, including generation/replay, supplied validation, pure verification and several identity passes, is an illustrative provisioning scenario. It is not an upper bound: extra scope passes, throttling, slow storage, many interruptions or semantic acquisition can exceed it. Three distinct equally large scope files can roughly triple the dominant I/O/CPU work; twelve equal-size jobs are a worst-case planning scenario, not established scope sizes.

CPU: generation/replay and native validation are predominantly single-worker work; elapsed estimates are also order-of-magnitude CPU allocations where CPU-bound. Storage waits, scheduler hashing, full Python model/ledger costs and source signing are not measured at retained scale. Reserve one dedicated sequential worker and **8 GiB RAM initially**, with hard stop on approaching that allocation; this reserve is not a proven full-model RSS bound. Parent and child observations are reported separately above. No memory benefit is inferred from adding workers. Qualify the actual host and bounded metadata/semantic load after inputs are known, before committing to full execution.

Disk:

- Mechanical hash-only job: reserve 4 GiB for descriptors, journals, packaged/restored metadata and temporary work **in addition to** the actual extracted parent/predecessor tree measured on the target. No binary/table retention is claimed.
- Optional materialized binary: add 729.26 GB plus durable-copy headroom; accepted hash-only binary generation needs none of this output storage.
- One distinct full static TSV: approximately 19.91 TB source bytes. Conservative source + retained acquisition/snapshot copy + 25% headroom is **49.78 TB**, plus all semantic source/index/ledger storage.
- Three distinct full static TSVs under that two-copy policy: **149.33 TB** plus semantic storage. Twelve equal-size phase/scope files: **597.33 TB** scenario. Sharing or deleting copies requires an explicit verified lifecycle/storage plan; do not assume automatic deduplication.
- Equality indexes, source snapshots, SQLite directories, events and qualification/assessment artifacts add storage proportional to actual inputs, currently unknown. No finite total peak is invented. Compare manifest lengths before admitting a storage budget.

The current ~26 GB free scratch volume can hold this preflight and descriptors; it cannot hold a full binary file or textual supplied stream. A host/storage decision is required. Exact numeric estimates and measurement references are in plan/RESOURCE-ESTIMATES.json.

## Recovery schedule, progress and stop budgets

**Generation/replay:** use the persisted contiguous intervals above, one segment per invocation initially, `--seconds 50`. Every segment has input/output cumulative SHA-256 state, exact segment digest/row/byte count and chain identity. Pause before the next segment with PAUSE; an interrupted uncommitted .part is ignored. fsync/rename and verified durable backups after each batch limit loss to the unbacked suffix. Shrink only an uncommitted interval if a segment exceeds budget. A changed interval size is not a universe change. Standalone segment digests do not produce the final hash: only contiguous header-anchored SHA state updates through every interval, with completed replay, establish exact whole-stream SHA-256. Binary replay uses the direct predicate engine; TSV replay is the same generator, so the independent supplied-row validator remains required.

**File-backed collector:** preserve stable absolute paths, exact input manifest/trusted bytes, scheduler key, collector checkpoint, stage/input catalogs, source snapshots/indexes, native and crypto journals and prerequisites. Quiescent inputs plus a trusted executor/key/code boundary are required within an invocation; permissions, mtime, advisory locks and journal possession are not cryptographic identity or source qualification. Each new invocation rehashes exact inputs/artifacts before reuse. Changed bytes, stale code/backend/profile or substituted prerequisites reject. A trusted journal detects alteration within its key boundary; it is not evidence authority.

Native link recovery retains consumed byte position, SHA-256 state, partial row/parser state, last tuple/ordinal and separate counts, and **rereads the entire consumed source prefix to establish byte identity** before advancing. Read-ahead is not committed consumption. Index startup repeats. Acquisition can rebuild exact partial object/constituent prefixes; interrupted semantic/event work may rebuild maps and restart value validation while reusing verified snapshots/indexes.

Pure Ed25519 reconstructs its verification state by rereading the exact original-message prefix. No safe export of live verification state is implemented. A pause at 50% of a 19.91 TB message adds about **9.96 TB** of prefix processing at that stage, before new work; scheduler rechecks are additional. Resuming at the same frontier without enough deadline can produce no progress. Total replay for fixed small progress quanta q is roughly N(N/q−1)/2 bytes. The default 64 MiB/50-second pattern is operationally unsuitable at TB scale, despite functional correctness on bounded fixtures.

Recommended practical schedule after input/host qualification: use long-lived bounded **stage-sized** invocations, set `--new-bytes` at least the largest supplied file and `--auth-new-bytes` at least the largest original signed message, and keep durable checkpoints/progress logs. A provisional 30-day collector deadline for one complete sequential job is a planning stop budget, not a performance promise. Termination must allow atomic checkpoint completion. Avoid periodic short restarts; a restart budget must include full input hashing + all saved-prefix reconstruction + intended new work. Reduce scope only if source law defines that scope, never to meet runtime budgets.

Progress records: generator interval/frontier/total and exact cumulative bytes; collector stage label, source path identity, consumed offset, replay target, new bytes, separate structural/potential counters and stage completion. Save logs and checkpoints to durable storage; record generation, replay, validation and authentication completion independently. Stop immediately on any identity/semantic/authentication rejection, storage below reserved headroom, RAM nearing the approved reserve, missing prerequisites or lack of forward progress after a fully costed reconstruction interval. Collect and preserve ordered failures; never convert a stop into success. At the generation stage, stop for review if aggregate runtime exceeds 2 hours for binary generation+replay or 48 hours for TSV generation+replay on the planned host. These are review stops, not automatic relaxations.
