# Full-universe obligations and execution plan

## What is and is not compactly established

The retained predicate is exactly `left.arbitrary OR right.arbitrary OR equal symbolic_digest`, for zero-based `i < j` in numeric lexicographic order. Across 426,984 tokens there are 91,157,454,636 possible unordered pairs. Exactly 50 tokens are non-arbitrary, in 18 symbolic-digest groups. The excluded set comprises precisely the non-arbitrary pairs with unequal digests: 1,169 exclusions. Therefore **91,157,453,467 pairs** are included. `inputs/pairs.txt` is a lossless descriptor of this predicate, not a replacement stream hash.

This reduction follows the predicate by Boolean complement. Checking all saved token classifications, then the 1,225 fixed/fixed candidates, is an exact count and set-description method. It neither samples nor omits any arbitrary/constant, old/new or cross-record combination. Repeated identical-looking records keep their original distinct indices and IDs. CP2's verified token/provenance expansion remains authoritative input to this calculation.

## Sizes and measurements

Exact binary size: **729,259,627,770 bytes** (729.26 GB decimal; about 679.18 GiB), including the 34-byte domain header.

The exact equality-only TSV size is **19,908,491,206,656 bytes**. Structural rows and their effect on ordinal width raise this. A conservative, verified upper bound is **19,911,077,213,024 bytes**: about **19.91 TB** for one complete links file. The bound allows all 4,368,254 structural occurrences, relation classes up to 256 bytes (actual retained maximum verified: 38), and maximum token-ID length 157. Duplicate wire tuples are removed without collapsing provenance-distinct relation orders. This is a bound, not a reported full byte-stream count. L64 remains sufficient; the six-digit link ordinal is a minimum width, not a million-row cap.

Twelve bounded benchmark processes completed in **38.973568 seconds combined**; the longest took **8.875131 seconds**. Initial six smaller measurements took 12.701003 seconds and are retained separately. Two preparation-authoring failures launched no benchmark worker. All process caps were 59 seconds or lower; aggregate benchmark execution remained below 180 seconds. Results are performance evidence only and do not establish full conformance, stream identity or semantic coverage.

Final measured binary throughput: approximately **497–550 MB/s**; final TSV throughput **476–535 MB/s**. Both workers compute two SHA-256 contexts (independent segment bytes and cumulative stream state). Measurements include worker startup, token/edge loading and TSV sorting. Peak child RSS was 12,544 KiB for binary, 483,584 KiB for TSV. This is the process-family maximum observed so far, not a claim of per-segment exact RSS. Host and CPU are in `results/benchmarks.json`.

Linear extrapolation gives **22–25 minutes per binary pass** and **10.3–11.7 hours per TSV pass**. Plan **30–60 minutes per binary pass** and **12–24 hours per TSV pass** on similar hardware. Complete replay approximately doubles each. Two binary passes plus generation/replay of one full TSV are therefore a **25–50 hour planning allocation**, excluding qualification, signature integration and extra streaming passes. Sustained throttling, lexical segment density, repeated startup, storage sync and different hardware are uncertainties, not measured multipliers. Signature and object hashing work must be benchmarked after its exact streaming integration; no runtime estimate for unimplemented cryptographic glue is presented as measured.

If all three bundle closures are proven to equal the full graph, their identical token/link byte files can share verified content; evidence rows and signatures still differ. Otherwise separately compute each exact closure. Never assume all three byte streams identical to save work. Extra signature/preimage passes can materially increase the schedule.

Hash-only working storage is modest: the native TSV descriptor is 236,894,099 bytes, the preserved package chain is tens of MB compressed, and journals are expected to total tens of MB. Reserve **2 GB** free scratch plus an external durable checkpoint destination and **1 GB RAM** per TSV worker (measured about 472 MiB); binary worker RAM is about 13 MiB. The current scratch volume has about 27 GB free, enough for hash-only work, not a binary table or TSV. Materializing requires at least 730 GB for binary or 20 TB for one TSV, plus safety/headroom; retaining three nonidentical full files can require about 60 TB. Hash-only storage does not make absent signed evidence present.

## Concrete recommended next execution

1. Preserve this package and verify its manifest. Keep accepted input hashes and the selected contract fixed. Rebuild native workers on the destination machine; a changed binary must use a new journal or independently replay into a new identity, not silently resume another build.
2. Before a full run, resolve the intended integration witness's remaining source/qualification/ledger/closure obligations. A mechanical full-stream computation can be a separate conditional milestone; label it accordingly and do not present it as admission. Do not run the current in-memory admission CLI against a multi-terabyte file.
3. Run binary generation in bounded **67,108,864-candidate segments** (about 536.9 MB output each), one segment per command/session slice initially. There are 1,359 segments. Persist each completed record off the ephemeral workspace after every bounded batch. Independently replay through the direct predicate engine, also in bounded slices; retain its completion cursor. A 50-second per-command deadline is provided.
4. For the TSV use **64 lexical source-token positions per segment** (6,672 segments). About 5–9 seconds was observed for the tested segments, but every worker retains its hard deadline. If a segment times out, shrink the next uncommitted segment; no accepted prefix changes. Generation and same-engine replay are reproducible; independent small Python oracles verify sorting, deduplication, orientation, ordinal spelling and byte framing. For high-assurance full verification, add an independently implemented streaming supplied-row validator with legal-membership/unique-order/cardinality checks; the current in-memory adapter expresses those checks but does not scale.
5. Test pause/resume and corruption handling on the execution machine before launching long sequences. `PAUSE` stops before the next segment. Kill/timeout discards only the uncommitted segment; `.part` is never a completion record. Keep the controller alive only for a bounded batch and resume from durable files, not chat continuity.
6. Only after complete contiguous generation AND complete replay, reconcile total rows/bytes, exact descriptor/model identity, and final SHA state. The `full_stream_sha256` field remains null until generation reaches the end. Treat that field as an unverified computed identity until replay also completes. For TSV, independent source/semantic and full supplied-row verification remain separate gates even after same-engine replay.
7. Place the genuinely computed binary digest into a newly constructed candidate model, then rebind all changed model/outer/input/argument/assessment/evidence identities in acyclic order. Preserve the CP2 provisional model as historical evidence. Integrate exact three-scope V2 pure-Ed25519 signatures and object framing with bounded resumable byte acquisition; do not switch to a prehash-signature variant. Re-run adversarial whole integration, qualification, actual/conditional boundary and precedence checks. Return a recoverable checkpoint before advancing further.

**Nothing in steps 2–7 was executed as a full-universe run in checkpoint 4A.** Full hashes, full-stream verification, complete integration witness, actual source qualification, actual profile admission and runtime kernel completion remain outstanding.
