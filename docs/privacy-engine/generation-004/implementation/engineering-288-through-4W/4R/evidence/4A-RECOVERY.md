# Recovery and final-identity rules

Each job is keyed to SHA-256 of the descriptor, both native source files, controller source and the exact worker executable. The descriptor comes from all hash-verified saved CP2 token/structural segments; `inputs/universe.json` and `inputs/links-inputs.json` retain those source identities. The selected contract is copied unchanged.

A pair segment covers a contiguous half-open range of ranks in the complete numeric `i < j` triangle, including excluded positions. Its row count excludes exactly the fixed/unequal cases. A TSV segment covers a contiguous half-open range of source-token positions after lexicographic token-ID sorting; target positions, relation-order cells and relation-class cells are merged in the required order. Every structural wire tuple is deduplicated; distinct relation provenance/orders survive. Source index orientation of equality pairs is never replaced with ID-sorted orientation.

`segment-NNNNNNNN.json` records the interval, exact generated row/byte count, SHA-256 of segment row bytes, input/output cumulative SHA states and finalization of the prefix state. Only the first cumulative state includes the exact appropriate header, once. Standalone segment digests never include that header. Nonzero-start benchmark prefixes are artificial `header + measured segment` prefixes and are NOT hashes of a genuine full prefix. Benchmarks are never adopted into a production journal.

SHA state is serialized as eight canonical hexadecimal 32-bit words, a decimal byte count, and exact pending bytes. It is not a dump of ABI padding or pointers. OpenSSL performs the SHA-256 update/compression/finalization; state export/import preserves buffered tail bytes and bit count. Tests compare an independent Python hashlib result for every cut of the tiny stream, including a segment containing no accepted rows. Same-build binary pinning is intentionally stricter than state-format portability.

The controller takes an exclusive nonblocking file lock, checks contiguous numbered records and the hash chain, and flushes/fsyncs each `.part`, renames it atomically, then fsyncs the directory. HEAD is written only after the segment file commits. A crash between those writes leaves a valid segment that can be adopted after continuity checks. A torn `.part` is ignored and recomputed. Missing/reordered committed segments, changed input/code/binary identities and damaged HEAD chains reject. Segment size may change only at the uncommitted frontier; it is not an input-universe change.

`PAUSE` in the journal directory prevents the next segment. Remove it to resume. Native processes time-check at buffer flushes and source-row boundaries; the Python controller imposes a separate hard timeout no greater than 60 seconds. A timeout/kill before the atomic commit produces no completion record. The native TSV startup read/sort may only be interrupted by the outer timeout. A running segment is intentionally allowed to finish after a PAUSE marker appears; a direct process termination loses at most that segment.

Generation prints frontier/total/percent after each committed segment; workers print row/elapsed progress when running for ten seconds. For TSV, the field named `candidate_frontier` means lexical source-token frontier, not pair cardinality. Filesystem STATUS is advisory; resume derives state from records, never trusts a progress percentage.

Verification replays saved intervals, recomputes exact bytes and compares both segment hash and cumulative-state transition. Binary replay uses a direct token predicate rather than complement lookup; TSV replay uses the same generator and is explicitly labelled as such. A separate `verification/verified-NNNNNNNN.json` chain persists checked progress so replay can also pause/resume. `results/recovery-demonstration` contains a complete tiny run: paused after one segment, an intentionally incomplete `.part` introduced, resumed without changing the first segment, exact stream independently reconstructed in Python, verification paused and resumed. Deadline cancellation, altered records, recomputed fraudulent record hashes, missing segments and changed inputs are also tested.

## How the final identity follows

For a journal anchored at rank zero, every committed interval starts exactly where its predecessor ends. The descriptor fixes the universe and ordering; no holes or overlap are accepted. Each segment's independently reproducible bytes update the predecessor's SHA-256 state. A complete verified chain ending at the full frontier therefore finalizes SHA-256 of **header || rows of segment 0 || rows of segment 1 || ...**, exactly the required stream. SHA-256 of concatenated segment hashes is never used as that identity. The journal-chain hash is only recovery metadata.

Segment hashes/state records are integrity checks, not signatures or trusted source qualification. An attacker who rewrites the whole journal, input identity and verification receipts is outside their authentication guarantee. Recheck the externally retained package identity and replay from the header when recovering from an untrusted store. An isolated segment can be verified against its input state, but only the entire header-anchored sequence establishes the final full-stream identity.

Keep accepted packages and completed journals in at least one durable external location. At each bounded batch, atomically snapshot/archive the journal, verify that snapshot's SHA-256, then sync it to the durable location and verify the receipt. The runner itself writes local durable files; it does NOT upload or guarantee survival of a wiped ephemeral workspace. Restarting from the last externally verified snapshot may repeat only later work. Do not rely on a long-lived chat process.

No table is written by the supplied workers: exact bytes are streamed into hashes and discarded. Reconstruction is deterministic from the pinned descriptor and intervals. Saving table bytes, delivering authenticated four-file evidence, and extending exact signature/object preimages need their own storage/acquisition implementation; the hash journal does not falsely claim those files exist.
