## 9. Exact three-result comparison

Every bounded comparison attempt shall evaluate in this order:

1. validate the successor generation, mapping, profile, authorization and occurrence identities and digests;
2. authenticate and validate every authoritative source and authority relation;
3. obtain every ordered projection component for authorized `Q0` and authoritative current protocol state;
4. apply the profile-defined canonicalization and normalization operations;
5. validate applicable preconditions, invariants, ordering coordinates and dependency coordinates;
6. apply the complete profile equivalence and material-conflict predicates;
7. produce exactly one result.

The result set is exactly:

- `equivalent`;
- `material-conflict`;
- `indeterminate`.

`equivalent` applies only when every prerequisite is authoritative, authenticated, available, valid, complete and canonicalizable and the profile equivalence predicate is true.

`material-conflict` applies only when every input required for the decision is authoritative, authenticated, available and valid and at least one profile-defined material-conflict predicate is established.

`indeterminate` applies when any required identity, digest, authority relation, source, input, authentication, availability, validity, completeness, canonicalization, normalization or comparison operation cannot be established.

Only `equivalent` permits execution or commitment.

Absence of equivalence is not proof of material conflict. Absence of material conflict is not proof of equivalence. `indeterminate` is neither equivalence nor material conflict.

### 9.1 Comparison identity and history

### 10.2 Blinded commitment mode

The commitment domain is exactly the UTF-8 byte string:

`PE-TSE-COMPONENT-COMMITMENT-V1`

1. commitment domain;

The component bytes use the profile-defined canonical representation. The blind is appended as exactly 32 raw octets without a length prefix.

The commitment value is:

`SHA-256(canonical-preimage)`

The digest is lowercase hexadecimal when represented as text.

The blind is confidential authoritative comparison material. It must not be reused across components or authorizations and must not become a reusable public identifier.

The commitment proves only equality of the complete bound preimage under the identified profile. It does not independently prove actor identity, enrollment, admission, provenance, broader state correctness, equivalence under another profile or any fact not encoded by that preimage.

Changing the digest algorithm or commitment grammar requires a distinct future protocol generation.

## 11. Recovery selection

- pre-execution `material-conflict`;
- pre-execution `indeterminate`;

- post-execution and pre-commitment `indeterminate`;

- commitment-boundary revalidation failure.

Each row selects exactly one disposition:

- `new-U-from-unchanged-D`;
- `new-E-new-D-new-U`.

`new-U-from-unchanged-D` is valid only where the profile-defined prerequisite predicate establishes that every affected, changed or unavailable component lies outside the Determination dependency set and that the earlier `D` remains authoritatively sufficient for a new authorization.

If that predicate is false or cannot be established, the disposition must be `new-E-new-D-new-U`.

The implementation does not select or override the disposition.

Every new Evaluation, Determination, authorization, transition occurrence and comparison attempt has an identity distinct from every predecessor occurrence. Every earlier occurrence and result remains immutable.

No failed occurrence may be repaired, resumed, reinterpreted or converted into a committed occurrence.

## 12. Atomicity and failure

The authoritative comparison shall occur:

- immediately before entry into bounded transition execution; and
- again against authoritative protocol state at the semantic commitment boundary.

A comparison followed by an intervening authoritative protocol-state change does not establish equivalence at commitment.

Comparison revalidation and commitment form one indivisible protocol-semantic decision.

This preserves:

`protocol-semantic atomicity != implementation transaction atomicity`

Before execution begins:

- `material-conflict` makes the authorization stale against that conflicting state;
- `indeterminate` produces pre-transition-failure semantics;
- neither result permits execution or commitment.

After bounded execution begins but before commitment:

- `material-conflict` or `indeterminate` prohibits commitment;
- no partial state may become authoritative;
- the occurrence reaches terminal transition failure.

Transition execution failure is terminal for that `U`. No partial commitment, alternate successor state, repaired authorization or substituted occurrence is permitted.

This determination does not prescribe or elevate a database transaction, blockchain transaction, consensus mechanism, lock, storage layout, instruction sequence, event model, rollback mechanism or implementation technology.
